# Размещение на личном сервере

Страница и серверный обработчик находятся в одной папке. React, npm-пакеты и сборка не нужны. Нужен Node.js 22 или новее с доступом по HTTPS к `profile.tutoronline.ru`.

## Локальный запуск

Откройте терминал в папке сайта и выполните:

```sh
node server.mjs
```

Откройте `http://127.0.0.1:8765/`. Сервер также обслуживает `/adaptive/`, чтобы сохранить адрес локального просмотра.
Обычный файловый хостинг или Python HTTP server не выполняет `server.mjs`, форма с ним работать не будет.

## Публичный сервер

1. Скопируйте содержимое архива в отдельную папку на сервере.
2. Запустите Node.js как постоянную службу от отдельного непривилегированного пользователя.
3. Укажите `PUBLIC_ORIGIN` — адрес своего сайта с протоколом, без пути и завершающего слеша.
4. Настройте HTTPS и обратный прокси на `127.0.0.1:8765`.
5. Проверьте одну помеченную тестовую заявку с разрешённым номером, найдите её в CRM и проверьте все поля.

Пример запуска (замените адрес на свой):

```sh
PUBLIC_ORIGIN=https://math.example.com TRUST_PROXY=1 node server.mjs
```

Пример блока Nginx внутри уже настроенного HTTPS-сервера:

```nginx
location / {
    proxy_pass http://127.0.0.1:8765;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 25s;
    client_max_body_size 16k;
}
```

Это фрагмент настройки прокси, не готовая настройка домена и сертификата. `TRUST_PROXY=1` принимает адрес клиента из `X-Real-IP` только от локального прокси; Nginx должен перезаписывать этот заголовок, как в примере.
По умолчанию Node слушает только localhost. Для контейнера при необходимости задайте `HOST=0.0.0.0`, но не публикуйте этот порт в обход HTTPS-прокси.

## Вебхук и поля

Адрес по умолчанию уже задан на сервере:
`https://profile.tutoronline.ru/DataService.svc/SaveRegistrationRequest`.

Сервер отправляет POST `application/x-www-form-urlencoded` с шестью полями:

| Поле | Значение |
|---|---|
| `name` | Имя из формы |
| `phone` | Телефон из формы |
| `email` | Email из формы; может быть пустым |
| `subject` | Математика |
| `landing` | Адрес страницы с пятью стандартными UTM-параметрами, если они есть |
| `info` | Заявка с лендинга по математике. Запись на бесплатный урок-диагностику. |

`goal`, `info1`, `info2` не отправляются. Произвольные параметры URL, фрагмент адреса и cookies не передаются.
Требуемое согласие проверяется на клиенте и сервере. Согласие на рекламу не передаётся в эти шесть полей и не должно автоматически считаться полученным в CRM.

В Тильде есть отдельная настройка отправки JSON. Если она использована у вас, задайте на сервере `LEAD_WEBHOOK_FORMAT=json`; по умолчанию выбран обычный формат формы. Имя параметров и фактический ответ именно вашего обработчика ещё нужно подтвердить реальным тестом.

## Подтверждение результата

После успешного HTTP-ответа вебхука сервер дополнительно ждёт явный признак успеха: `ok`, `true`, JSON с `success: true` или `Success: true`, либо такой результат в `SaveRegistrationRequestResult`.
Произвольный HTML, пустой HTTP 200 и отрицательный результат не считаются подтверждением.
Если ваш обработчик возвращает другой ответ, нужно сначала установить его смысл и скорректировать `isConfirmed` в `server.mjs`.

При неопределённом результате посетителю предлагается уточнить запись по телефону. Автоматических повторных отправок нет.
Для одной и той же формы браузер сохраняет ключ попытки; сервер повторно возвращает уже полученный результат, не дублируя запрос к вебхуку в течение 10 минут.
Защита от повторов и лимиты хранятся в памяти одного процесса и сбрасываются при перезапуске. Для нескольких экземпляров сервера нужен общий механизм хранения.
Персональные данные заявок в журналы этого сервера не записываются; постоянного хранения или очереди заявок здесь нет.

## Что проверено, а что осталось

27 октября 2026 проверена цепочка браузер → локальный сервер → тестовый ответ вебхука → сообщение формы.
Проверены формат данных, кириллица, UTM, согласие, успех, неопределённый результат, таймаут, повторный запрос и недоступность серверных файлов через HTTP.
Реальные заявки в CRM при этих проверках не создавались. Работоспособность интеграции с CRM окончательно подтверждается только после реальной тестовой заявки и проверки её в CRM.
