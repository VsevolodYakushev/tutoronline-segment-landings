# Research: Три сегментных лендинга с квиз-формой брони

**Feature**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Date**: 2026-11-05

Исходные данные проанализированы:
- ТЗ — 8 разделов: KPI, сегменты, оффер, каркас из 10 блоков, дефицит и плавающие элементы, форма, адаптив, аналитика.
- Базовый лендинг `Design System/tutoronline-adaptive/`: статический HTML, `styles.css` с токенами, `app.js`, `server.mjs` на Node 22+ с отправкой в вебхук `SaveRegistrationRequest`.
- Дизайн-система `Design System/`: 83 SVG-иконки, 4 логотипа, шрифт Graphik 400/500 в TTF.

Каждое решение записано в формате: решение → обоснование → рассмотренные альтернативы.

---

## R1. Технологическая основа страниц

- **Decision**: Статические HTML/CSS/JS без фреймворка, как у базового лендинга. Три страницы собираются одним скриптом `build.mjs` на встроенных модулях Node (без npm-зависимостей) из общего шаблона и JSON-контента сегментов.
- **Rationale**: Базовый лендинг конвертирует и уже работает без React и сборки; ТЗ требует строить новые лендинги «на его базе». HTML, отрендеренный на этапе сборки, даёт лучший LCP (≤ 2,5 с на 4G), видимость контента без JS и минимальный вес для встроенных браузеров маркетплейсов. Шаблон с контентом в JSON исключает тройное дублирование разметки.
- **Alternatives considered**: (1) Три вручную поддерживаемые копии HTML — расхождения при правках, втрое больше работы. (2) Одна страница с подстановкой сегмента в браузере — хуже LCP, без JS контент пуст. (3) Astro/Next/Vite — лишняя инфраструктура и npm-зависимости ради трёх страниц, расходится с базовым стеком.

## R2. Шаблонизация в `build.mjs`

- **Decision**: Шаблоны — ES-модули `src/templates/*.mjs`, экспортирующие функции `(ctx) => string` на тегированном литерале `html`, который экранирует подстановки. Контент — `src/content/*.json`.
- **Rationale**: Нулевые зависимости, циклы и условия на обычном JS (списки репетиторов, болей, FAQ), безопасное экранирование, понятно любому фронтендеру.
- **Alternatives considered**: Handlebars/Nunjucks — npm-зависимость ради трёх страниц; самописный `{{ }}` без циклов не покрывает списки.

## R3. Источник дизайна

- **Decision**: Токены `:root` из `styles.css` базового лендинга (цвета `--primary #5756b3`, `--accent #ff5247`, `--success #27ae60`, отступы, радиусы, типографика desktop/mobile) выносятся в `tokens.css` без изменений. Компоненты, нужные по ТЗ (кнопки `btn-l btn-accent`, карточка репетитора `tut-card`, стекло `hx-glass`, FAQ, рейтинги площадок), переносятся точечно. Всю 99-килобайтную `styles.css` целиком не подключаем. Иконки — SVG из `Design System/icons`, логотипы — `logo_*.svg`.
- **Rationale**: Сохраняем визуальный язык конвертирующей страницы и укладываемся в бюджет LCP. Новые элементы (плашка таймера, стикеры, чипы, слоты, «билет») собираются только на токенах.
- **Alternatives considered**: Подключить `styles.css` целиком — лишний вес и конфликты со стилями старых блоков. Перерисовать дизайн с нуля — нарушает требование ТЗ.

## R4. Шрифт и изображения

- **Decision**: Graphik 400/500 конвертируется один раз из TTF в WOFF2 (`fonttools`, только при подготовке ассетов). Начертание 500 подгружается через `preload`, `font-display: swap`. Фото репетиторов и hero — WebP плюс AVIF с `srcset` на ширины 160/320/500/640; изображение первого экрана получает `fetchpriority="high"`, остальные — `loading="lazy"`. Конвертированные файлы коммитятся в `landings/assets/`, сборка от конвертера не зависит.
- **Rationale**: Требования ТЗ «WebP/AVIF со srcset, LCP ≤ 2,5 с»; TTF по 200 КБ — главный блокер отрисовки текста.
- **Alternatives considered**: Конвертация в каждой сборке через `sharp` — npm-зависимость с нативными бинарями на Windows и на сервере; оставить TTF/JPG — проваливает LCP.

## R5. Состояние посетителя: число мест, дедлайн, вариант

- **Decision**: Для каждого сегмента хранится запись `tst_v1_<seg>` = `{ seats, deadline, booked, variant, expired }`:
  1. **Сервер** при первой отдаче страницы сегмента без cookie выставляет `Set-Cookie: tst_v1_<seg>=<seats>.<deadlineTs>.<variant>; Max-Age=2592000; Path=/; SameSite=Lax; Secure`. Значения: `seats` — равномерно случайное 3–10, `deadline` — now + `timerMinutes` (15).
  2. **Клиент** зеркалит запись в `localStorage` (обёрнуто в try/catch). Если cookie пропала, а `localStorage` жив, cookie восстанавливается; если пропало всё — запись генерируется на клиенте.
  3. **Фолбэк без хранилищ**: `seats = 3 + hash(visitorId + seg) mod 8`, где `visitorId` — clientID Яндекс Метрики (если доступен), иначе отпечаток браузера `fnv1a(userAgent + language + размер экрана + часовой пояс)`; дедлайн в этом режиме живёт в памяти вкладки.
  4. Отображаемое число = `max(1, seats − booked)`.
- **Rationale**: ITP в Safari ограничивает cookie, выставленные скриптом, 7 днями, а серверную `Set-Cookie` с того же домена — нет, поэтому серверная cookie надёжнее даёт обещанные ТЗ «30 дней». Ключ с сегментом соответствует ТЗ (`slots_v1_5-9`). Детерминированный хэш выполняет требование ТЗ для недоступного хранилища.
- **Alternatives considered**: Только `localStorage` — теряется во встроенных браузерах и в Safari через 7 дней. Хранить состояние на сервере по IP — персональные данные, ошибки за NAT. Брать число мест из реального расписания — заказчик выбрал вариант из ТЗ (см. Clarifications).

## R6. Таймер оффера

- **Decision**: Таймер считает от абсолютного `deadline` (UTC ms), а не от «оставшихся секунд». Отрисовка — `setInterval` раз в 1 с с коррекцией по `Date.now()`; при `visibilitychange` обновляется сразу. Последние 60 с — класс `is-urgent` (`--accent`). Событие `lp_timer_expired` отправляется один раз на запись (флаг `expired`). После истечения: бейдж «−1500 ₽» → «сгорела», перечёркивание, кнопка и пробный остаются.
- **Rationale**: Перезагрузка не сбрасывает таймер; фоновые вкладки и спящие телефоны не «замораживают» отсчёт.
- **Alternatives considered**: `requestAnimationFrame` — лишняя нагрузка ради секундной точности; хранить оставшееся время — сбрасывается и дрейфует.

## R7. Слоты и холд места

- **Decision**: Слоты условные: в `schedule.json` задан шаблон недели для каждого репетитора (будни 16:00–20:00, выходные 11:00–15:00, шаг 1 ч, МСК). Клиент показывает ближайшие 3 дня, где есть слоты, начиная не раньше чем через 3 часа от текущего времени (правило ТЗ «предупрежу за 3 часа»). Время выводится с пометкой «МСК». Холд «Место закреплено за вами 10:00» — клиентский отсчёт без серверной блокировки. По истечении холда выбор слота сбрасывается с сообщением, контакты сохраняются.
- **Rationale**: Вариант с условными слотами принят заказчиком, бронь подтверждает менеджер. Серверная блокировка без реального расписания ничего не гарантирует, но усложняет систему.
- **Alternatives considered**: Интеграция с расписанием TutorOnline — нет доступа и API, не входит в объём. Слоты «на любой день» без 3-часового отступа — противоречат тексту обязательства.

## R8. Квиз-форма

- **Decision**: Один компонент `quiz.mjs` — конечный автомат `step1 → step2 → step3 → submitting → ticket | error`, все данные в одном объекте состояния (кнопка «Назад» ничего не теряет). Черновик сохраняется в `sessionStorage`, чтобы не пропадал при случайной перезагрузке.
  - Шаг 1: чипы классов сегмента и предметов «Математика» (выбрана по умолчанию) и «Русский язык». Класс предвыбирается из URL-параметра `grade`, иначе берётся `segment.defaultGrade` (1–4 → 2, 5–9 → 7, 10–11 → 11); смена — одним касанием.
  - Шаг 2: до 3 карточек репетиторов выбранного предмета и слоты; `?tutor=<id>` или кнопка «Хочу к этому репетитору» предвыбирают репетитора и ставят его первым, остальные — по порядку `segment.tutorIds[subject]`.
  - Шаг 3: имя, телефон с маской +7, обязательные чекбоксы (обязательство и согласие на обработку персональных данных), необязательное согласие на рекламу, необязательный блок «Заполните также для получения скидки» (email), плашка промокода, итог «~~1 500 ₽~~ 0 ₽».
  - Проверка полей — на `blur`. Анимации: `transform` за 240 мс, отключаются при `prefers-reduced-motion`.
- **Rationale**: Покрывает FR-015…FR-025 без зависимостей. Явный автомат упрощает тестирование и аналитику по шагам.
- **Alternatives considered**: Нативный `<form>` с тремя `fieldset` без автомата — сложнее держать состояние «Назад» и холд; библиотека форм — лишний вес.

## R9. Маска телефона

- **Decision**: Своя маска `+7 (XXX) XXX-XX-XX`: `inputmode="tel"`, `autocomplete="tel"`, размер шрифта 16 px. При вставке `8XXXXXXXXXX`, `7XXXXXXXXXX` и `+7…` нормализует номер. Валидно — ровно 10 цифр после +7.
- **Rationale**: Целевая аудитория — российские номера; маска уменьшает ошибки. Сервер по-прежнему принимает 10–15 цифр (совместимость).
- **Alternatives considered**: IMask/Inputmask — 10–30 КБ ради одного поля; без маски — больше ошибок ввода на мобильном.

## R10. Передача заявки в CRM

- **Decision**: Расширяется `server.mjs` базового лендинга (копия в `landings/server.mjs`). Endpoint `/api/lead` принимает новые поля и раскладывает их в шесть полей вебхука `SaveRegistrationRequest`:
  - `subject` — выбранный предмет;
  - `email` — из блока скидки;
  - `landing` — URL сегмента плюс 5 стандартных UTM;
  - `info` — структурированная строка: номер брони, сегмент, класс, репетитор, слот (МСК), промокод, запрос скидки, вариант, `utm_source`, `utm_content` (ID объявления), согласие на рекламу.

  Номер брони `TO-XXXXXX` вычисляется на сервере из `Idempotency-Key` (стабилен при повторах) и возвращается клиенту. Логика подтверждения (`isConfirmed`), идемпотентность, лимиты и запрет логирования персональных данных сохраняются.
- **Rationale**: Вебхук проверен в базовом лендинге и принимает только эти 6 полей (`goal`, `info1`, `info2` не используются). Структурированное `info` передаёт все поля из FR-023 без изменения формата CRM.
- **Alternatives considered**: Новые поля вебхука — формат CRM не подтверждён, нужна доработка на стороне TutorOnline; отправка из браузера напрямую — CORS и утечка адреса вебхука.

## R11. Промокод 100%

- **Decision**: Промокод задаётся параметром `offer.promoCode` в конфигурации. Код не секретен: по ТЗ §3 он виден в форме на шаге 3 до отправки, а в «билете» показывается вместе с номером брони (к которой он «закреплён»). В CRM код уходит в `info`.
- **Rationale**: ТЗ: «код закрепляется за бронью»; реальный код и механизм его погашения — на стороне заказчика.
- **Alternatives considered**: Генерировать уникальные коды на лендинге — CRM их не знает, менеджер не сможет проверить.

## R12. Аналитика и A/B

- **Decision**: Модуль `analytics.mjs` отправляет события в `window.dataLayer` и, если в конфигурации задан `ymCounterId`, в Яндекс Метрику (`reachGoal` с параметрами `segment`, `variant`, `utm_source`, `utm_content`, `step`). События и их порядок — в [contracts/analytics-events.md](contracts/analytics-events.md).
  - Первичные UTM-метки (first-touch) хранятся 30 дней в той же записи посетителя.
  - A/B: вариант `a|b` назначается на сервере вместе с cookie и делится 50/50. Переопределение для QA — `?v=a|b`. Inline-скрипт в `<head>` ставит `data-variant` на `<html>` до отрисовки, чтобы не было мигания; альтернативный текст первого экрана и формы лежит в HTML и скрывается CSS.
- **Rationale**: Яндекс Метрика — стандарт для российского трафика с Avito, WB и Ozon. `dataLayer` уже используется базовым лендингом (`landing_lead_success`). Вариант в одной записи с числом мест — единая точка истины.
- **Alternatives considered**: Отдельные A/B-сервисы (Varioqub и т.п.) — внешняя зависимость и мигание; клиентское назначение варианта — мигание и рассинхрон с CRM.

## R13. Плавающие элементы и клавиатура

- **Decision**:
  - Верхняя плашка `position: fixed`, высота 44 px на мобильном (≤ 48); у `<body>` — `padding-top`, у якорей — `scroll-margin-top`.
  - Нижняя кнопка — `position: fixed; bottom: env(safe-area-inset-bottom)`, видимостью управляет `IntersectionObserver`, как в базовом `app.js` (скрыта на первом экране, у формы и футера).
  - При `focusin` на полях и при сжатии `visualViewport` (клавиатура открыта) нижняя кнопка скрывается, а плашка становится статичной.
  - Стикеры: `@keyframes` покачивания с паузой (цикл 4,5 с) и пульсирующая точка. Всё это отключается при `prefers-reduced-motion`.
- **Rationale**: Требования ТЗ из раздела 5 и проверенная механика базового лендинга.
- **Alternatives considered**: `position: sticky` для нижней кнопки — не работает внутри контейнеров с `overflow: hidden`, которые есть в базовых секциях.

## R14. Тестирование

- **Decision**:
  - Unit-тесты на `node --test` для чистых модулей: склонение, состояние посетителя и хэш-фолбэк, таймер, генерация слотов, маска телефона, автомат квиза, сборка `info`, номер брони, `isConfirmed`.
  - Серверные тесты с подменой `upstreamFetch`, как в базовом лендинге.
  - E2E — `@playwright/test` (единственная dev-зависимость): Chromium и WebKit, ширины 360/390/768/1024/1440, сценарии из [quickstart.md](quickstart.md).
  - Встроенные браузеры Avito, WB и Ozon проверяются вручную на устройствах.
- **Rationale**: Проверяются критерии приёмки ТЗ (перезагрузка таймера и мест, 3 шага, адаптив); WebKit приближает поведение Safari iOS.
- **Alternatives considered**: Только ручная проверка — критерии SC-005, SC-007 и SC-008 нельзя повторять регрессионно; Cypress — нет WebKit.

## R15. Адреса страниц и хостинг

- **Decision**: Страницы публикуются по адресам `/1-4/`, `/5-9/` и `/10-11/` на одном домене. `server.mjs` отдаёт собранный `dist/` по белому списку, на `/` — редирект на `/5-9/` (самый массовый сегмент). Деплой — как у базового лендинга: Node 22+ за Nginx с HTTPS.
- **Rationale**: ТЗ «сегмент в URL», общие ассеты кэшируются между сегментами, одна cookie-область.
- **Alternatives considered**: Поддомены — три сертификата и раздельные cookie; query-параметр `?seg=` — хуже для модерации объявлений и аналитики.
